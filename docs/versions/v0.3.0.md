# Auditoria técnica e atualização — v0.3.0

## Objetivo

Transformar a fundação da locadora em um fluxo operacional completo até a confirmação
de disponibilidade: contexto automático, cadastro assistido, orçamento reproduzível e
reserva temporal sem sobreposição. Contrato e execução da locação permanecem fora deste
incremento.

## Entregas integradas

- organização ativa derivada do usuário autenticado;
- onboarding transacional de locadora, matriz e proprietário;
- cadastro assistido de até 100 equipamentos com códigos internos concorrentes;
- orçamento com período, múltiplas linhas e snapshots de preço;
- consulta de disponibilidade por estabelecimento, modelo e intervalo;
- bloqueio do envio de orçamento sem disponibilidade integral em uma única filial;
- condição operacional e agenda separadas na lista de equipamentos;
- confirmação somente a partir de orçamento enviado;
- alocação de unidades físicas específicas;
- cancelamento com liberação e preservação de histórico;
- proteção multi-tenant em formulários, views e serviços;
- bloqueios transacionais e exclusão temporal PostgreSQL;
- telas operacionais, testes e documentação para os quatro fluxos.

## Atualização da v0.2.2

Antes de atualizar um ambiente com dados reais, faça backup do PostgreSQL e confirme
que a restauração foi testada. Depois, atualize a aplicação e execute as migrations uma
única vez antes de liberar o tráfego.

Com Docker Compose:

```bash
git pull --ff-only origin main
docker compose up -d --build
docker compose exec web python manage.py migrate
docker compose exec web python manage.py check
```

Em uma instalação sem Docker:

```bash
git pull --ff-only origin main
uv sync --frozen --all-groups
uv run python manage.py migrate
uv run python manage.py check
```

Migrations novas desde a v0.2.2:

| Migration | Efeito |
|---|---|
| `catalog.0006` | cria a sequência por locadora e a inicializa acima dos códigos `EQ-*` existentes |
| `catalog.0007` | troca somente o rótulo de `AVAILABLE` para **Apta para locação** |
| `quotations.0001` | cria orçamentos, itens, snapshots e constraints |
| `reservations.0001` | cria reservas e alocações e protege sobreposição no PostgreSQL |

`reservations.0001` executa `CREATE EXTENSION IF NOT EXISTS btree_gist`. No Docker, o
usuário proprietário do banco possui a permissão necessária. Em produção gerenciada,
a migration deve ser executada por uma identidade autorizada a habilitar a extensão ou
depois que o operador do banco a tiver habilitado. A atualização é aditiva: não remove
clientes, ferramentas, preços ou perfis patrimoniais existentes.

Depois da migration, uma conferência rápida pode usar:

```bash
uv run python manage.py showmigrations catalog quotations reservations
```

Todas as migrations listadas devem aparecer marcadas com `[X]`.

## Regra temporal

Orçamento, reserva e alocações usam `[início, fim)`. Há sobreposição quando:

```text
existente.início < novo.fim E existente.fim > novo.início
```

Assim, `08:00–10:00` e `10:00–12:00` são períodos adjacentes e podem usar a mesma
unidade. Alocações com `released_at` preenchido permanecem no histórico, mas deixam de
participar do bloqueio.

## Concorrência e banco

`confirm_reservation()` usa transação e bloqueios de linha. No PostgreSQL, a extensão
`btree_gist` permite uma constraint de exclusão que combina:

- igualdade de `tool_unit_id`;
- sobreposição de `TSTZRANGE(starts_at, ends_at, '[)')`;
- condição `released_at IS NULL`.

Essa constraint protege até escritas que não passam pelo serviço. A migration é aditiva
e não exige transformação de dados anteriores. Em SQLite, a operação de banco é
ignorada intencionalmente; CI e produção PostgreSQL são a evidência concorrente.

## Estados e integração

Reservas possuem somente `CONFIRMED` e `CANCELLED`. Não existe rascunho porque o
orçamento cumpre esse papel. Uma reserva confirmada bloqueia o encerramento comercial
do orçamento; o usuário deve cancelar e liberar as alocações primeiro.

Confirmar uma reserva não muda `ToolUnit.status`. O campo continua descrevendo condição
operacional (`AVAILABLE`, manutenção, dano etc.), enquanto a agenda é calculada pelos
intervalos. Isso permite reutilizar a unidade em períodos futuros não sobrepostos.

## Limitações conhecidas

| Área | Limitação | Evolução candidata |
|---|---|---|
| Filiais | uma reserva usa um único estabelecimento | divisão controlada por item |
| Seleção | unidades são escolhidas automaticamente por código | escolha manual justificada |
| Expiração | não existe prazo automático da reserva | job idempotente com política |
| Contrato | reserva não representa aceite jurídico | módulo de contratos da v0.4 |
| Operação | retirada, devolução e inspeção não existem | eventos operacionais da v0.4 |
| SQLite | não possui exclusão temporal concorrente | usar PostgreSQL para homologação |
| Auditoria | timestamps não identificam o usuário da ação | eventos de domínio com autor |
